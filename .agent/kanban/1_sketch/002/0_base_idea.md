# Идея: VSCode Extension + Дистрибуция

## Введение

Развитие утилиты `forge` в сторону экосистемы:
1. VSCode Extension — графическая Kanban-доска для удобной работы с `.agent/kanban/`
2. Дистрибуция — сайт/маркетплейс для скачивания плагина и документации

---

## VSCode Extension

### Основные возможности

1. **Графическая Kanban-доска**
   - Отображение всех стадий: backlog, sketch, design, todo, in_progress, done
   - Drag & drop для перемещения задач между стадиями
   - Цветовая кодировка по типу задачи (feature, fix, spike, chore)
   - Приоритеты с визуальными индикаторами

2. **Работа с задачами**
   - Создание новых задач (всплывающее окно с формой)
   - Редактирование задач через webview panel
   - Просмотр истории изменений задачи (git log)
   - Поиск и фильтрация задач

3. **Git-интеграция**
   - Отображение текущей ветки и связанной задачи
   - Автоматическое создание веток при перемещении задачи в todo
   - Быстрые команды: Start Work, Done, Create PR
   - Показ коммитов, связанных с задачей

4. **Мульти-агентная система (Arch / Dev / Ops)**
   - Три роли агентов с разными моделями для оптимизации затрат
   - Автоматический роутинг запросов к нужной роли
   - Настройки стоимости и лимитов
   - Визуализация активности каждой роли

5. **Локальный LLM (через OpenRouter)**
   - Чат с LLM в боковой панели
   - Генерация идей/скетчей задач
   - Анализ кода и предложений изменений
   - Выбор провайдера и модели через настройки

### Техническая реализация

- **Язык:** TypeScript (стандарт для VSCode extensions)
- **Framework:** VSCode Extension API + React для webview
- **State management:** VSCode Memento (для сохранения настроек) + чтение `.agent/kanban/` файлов
- **LLM integration:** OpenRouter API
- **Git integration:** Simple Git или прямые вызовы git CLI
- **Agent orchestration:** Лёгкий роутер для распределения запросов между ролями

## Дистрибуция

### Вариант A: Простой сайт (landing page)

**Структура:**
- Страница проекта: описание Forge, скриншоты, демо-видео
- Ссылка на VSCode Marketplace (через официальную публикацию)
- Документация (как в README.md, но красиво оформленная)
- FAQ и гайды

**Технологии:**
- Статический сайт: Next.js или Astro
- Хостинг: Vercel или GitHub Pages
- Домен: forge.dev или forge.cli (если доступен)

**Плюсы:**
- Быстро реализуется
- VSCode Marketplace даёт органический трафик
- Минимум затрат на поддержку

**Минусы:**
- Зависимость от Microsoft (VSCode Marketplace)
- Ограниченные возможности аналитики

### Вариант B: Собственный маркетплейс

**Возможности:**
- Регистрация пользователей
- Личный кабинет с подписками (если сделаем платные функции)
- Аналитика использования
- Обратная связь и баг-репорты
- Сообщество (форум/дискорд)

**Технологии:**
- Backend: Rust (Actix-web) или Node.js (Next.js API routes)
- Frontend: Next.js + shadcn/ui
- БД: PostgreSQL
- Auth: NextAuth или собственное решение

**Плюсы:**
- Полный контроль над пользователями и аналитикой
- Возможность монетизации
- Сильное комьюнити

**Минусы:**
- Высокие затраты на разработку и поддержку
- Нужно привлекать трафик (SEO, маркетинг)

### Вариант C: Гибридный (рекомендую)

1. **Этап 1:** Простой сайт + VSCode Marketplace
   - Быстрый запуск, минимальные затраты
   - Проверяем интерес пользователей

2. **Этап 2:** Расширяем сайт (если есть интерес)
   - Добавляем логин, аналитику

   - Платные функции или подписки

## Мульти-агентная архитектура

### Три роли агентов

```
┌──────────────────────────────────────────────────────────┐
│  1. Arch (Архитектор)                                    │
│  Модель: Claude Sonnet / GPT-4o / o3                     │
│  Задачи:                                                 │
│  - Анализ требований                                     │
│  - Проектирование архитектуры                            │
│  - Принятие решений (какие файлы менять, какой подход)    │
│  - Декомпозиция задач                                    │
│  - Code review                                           │
│  Стоимость: $$$                                          │
├──────────────────────────────────────────────────────────┤
│  2. Dev (Разработчик)                                    │
│  Модель: Claude Sonnet / GPT-4o-mini / DeepSeek Coder    │
│  Задачи:                                                 │
│  - Написание кода по плану от Arch                       │
│  - Рефакторинг                                           │
│  - Написание тестов                                      │
│  - Исправление багов                                     │
│  Стоимость: $$                                           │
├──────────────────────────────────────────────────────────┤
│  3. Ops (Оператор)                                       │
│  Модель: GPT-4o-mini / Haiku / Gemma / локальная         │
│  Задачи:                                                 │
│  - Создание/перемещение файлов                           │
│  - Git операции (commit, push, branch)                   │
│  - Запуск тестов и сборок                                │
│  - Форматирование, линтинг                               │
│  - Простые шаблонные операции                            │
│  Стоимость: $                                            │
└──────────────────────────────────────────────────────────┘
```

### Маппинг ролей на стадии Kanban

| Стадия Kanban | Роль агента | Модель |
|---------------|-------------|--------|
| `1_sketch` | **Arch** | Сильная (рассуждения) |
| `2_design` | **Arch** | Сильная (финализация) |
| `3_todo` | **Arch → Dev** (передача) | Arch декомпозирует, Dev получает план |
| `4_in_progress` | **Dev** + **Ops** | Dev пишет код, Ops коммитит/создаёт файлы |
| `5_done` | **Ops** | Перемещение файла, финальный коммит |

### Оркестратор (Router)

Лёгкий маршрутизатор, который определяет какую роль вызвать:

**Вариант A: Правила (без LLM)**
- Если операция = git/файловая → Ops
- Если операция = код → Dev
- Если вопрос/решение → Arch

**Вариант B: Классификатор**
- Маленькая модель (Haiku) определяет тип задачи и маршрутизирует

### Настройки стоимости

```toml
[agents]
arch_model = "anthropic/claude-sonnet-4-20250514"
dev_model = "deepseek/deepseek-coder"
ops_model = "google/gemma-2-9b-it"  # или локальная через Ollama

[agents.cost_limits]
daily_budget = 5.00  # USD
arch_max_per_task = 0.50
dev_max_per_task = 0.30
ops_max_per_task = 0.05
```

### Преимущества

1. **Экономия до 60-70%** — Ops берёт на себя рутину на дешёвой модели
2. **Качество решений** — Arch не отвлекается на рутину
3. **Конкурентное преимущество** — ни Cline, ни Cursor не делают такое разделение

## Приоритеты

2. Drag & drop между стадиями
3. Создание/редактирование задач

4. Мобильное приложение (Tauri или native)

## Платные функции (Phase 3+)

### Jira/Trello синхронизация

**Возможности:**
- Двусторонняя синхронизация с Jira, Trello, Linear, GitHub Projects
- При `forge task move 001 in_progress` → задача автоматически обновляется в Jira
- При обновлении в Jira → файл в `kanban/` обновляется (через webhook или polling)
- Команда и менеджер видят изменения в реальном времени

**Модель монетизации:**
- **Бесплатно:** Forge CLI + VSCode Extension (локальная kanban-доска для соло-разработки)
- **Pro/Team ($X/месяц):** Синхронизация с Jira/Trello, командная работа, аналитика

**Техническая реализация:**
- API интеграции с Jira/Trello/Linear
- Webhook сервер для приёма изменений
- Конфигурация в `forge.toml`:
  ```toml
  [sync]
  provider = "jira"
  url = "https://company.atlassian.net"
  project = "FORGE"
  api_key_env = "JIRA_API_KEY"
  ```

## Открытые вопросы

1. **LLM провайдер:** Только OpenRouter или поддержка нескольких (OpenAI, Anthropic, Together)?
2. **Аутентификация:** Нужна ли в первом релизе или оставить на Phase 2?
3. **Монетизация:** Планируется ли и если да, то какая модель (нескоьлко вариантов, как в Cline, B2B и т.п. или вообще другой путь) Начать например с простой версией, типа Free?
4. **Комьюнити:** Discord или Telegram для обратной связи?
5. **Лицензия:** MIT, Apache 2.0 или проприетарная?
6. **Оркестратор:** Правила (без LLM) или классификатор (с маленькой моделью)?
7. **Skills:** Нужен ли отдельный файл для каждой роли (Dev,  Ops)?
8. **Mobile control:** Управление с мобильного телефона, за тем, что делает ИИ агенты (плагин)?
9. **Самообновление:** Возможно есть смысл иметь команду forge --update (обновлять все вместе и плагин и т.п. или нет)?
10. **wrap:** команда для оборачивания имеющегося проекта в структуру .agent описания, надо подумать, если проект уже описан подобием нашей структурой, но возможно старой версии или измененной пользователем (в общем бардак). Надо как-то забрать из этой старой структуры проекта все полезное описание и формировать наше новое описание используя данные из проекта. Это 100% надо делать через ИИ.
