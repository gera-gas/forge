# workflows/agent.md

## Роль этого файла
Этот файл описывает, как ИИ-агент (Claude Code, Cline, Aider и др.) должен взаимодействовать с задачами и контекстом проекта. Агент обязан следовать этим правилам при выполнении любой работы.

## Основные принципы
1. **Движение задач только вперёд** по конвейеру (sketch → design → todo → in_progress → done).
2. **Никаких возвратов задач назад**. Если нужно уточнение – создаётся задача-блокер в более ранней стадии.
3. **Одна активная задача** на агента (в папке `4_in_progress`).
4. **Коммиты и ветки** – по правилам `workflows/git.md`.

## Структура папки задач
Все задачи находятся в `docs/agent/tasks/` и имеют числовые префиксы для сортировки:

```
tasks/
├── 0_backlog/      # Отложенные задачи (не активны)
├── 1_sketch/       # Идеи, user stories, наброски
├── 2_design/       # Утверждённый дизайн / ТЗ перед реализацией
├── 3_todo/         # Технически проработанные задачи, готовые к коду
├── 4_in_progress/  # Задача, взятая в работу (не более одной)
└── 5_done/         # Завершённые задачи (история)
```

Каждый файл задачи – Markdown с YAML frontmatter (см. шаблон ниже).

## Формат файла задачи
```yaml
---
id: "001"                     # Уникальный номер (сквозная нумерация)
title: "Краткое название"
status: "sketch"              # Одна из: sketch, design, todo, in_progress, done, backlog
stage: "1_sketch"             # Путь папки (дублирует статус)
branch: null                  # Ветка Git (создаётся при переходе в todo)
created_at: 2025-04-14
updated_at: 2025-04-14
blocked_by: null              # ID задачи-блокера (если есть)
blocked_until: null
priority: "medium"            # low, medium, high, critical
tags: []
---
# Содержание задачи
... (описание, критерии приемки, ссылки на design/ или specs/)
```

## Жизненный цикл задачи

### Создание новой задачи
- **Команда:** `forge task new "Название" --stage sketch`
- **Действие:** создаётся файл в `tasks/1_sketch/` с заполненным frontmatter.
- **Git:** после создания пользователь делает коммит: `task(001): add sketch "Название"`

### Переход из sketch в design
- **Условие:** идея уточнена, есть user stories, принято решение развивать.
- **Действие:** файл перемещается в `tasks/2_design/`, `status` меняется на `design`.
- **Git коммит:** `task(001): promote sketch to design`

### Переход из design в todo
- **Условие:** дизайн утверждён, проведена техническая декомпозиция, задача готова к реализации.
- **Действие:** 
  - Файл перемещается в `tasks/3_todo/`, `status` → `todo`.
  - Создаётся Git-ветка: `feature/<id>_<slug>` (или `fix/...`), если её ещё нет.
  - `branch` в frontmatter обновляется.
- **Git коммит:** `task(001): approve design, create branch feature/001_short`

### Начало работы над задачей (in_progress)
- **Условие:** в `3_todo` есть задачи, в `4_in_progress` пусто.
- **Действие:** агент (или человек) выбирает задачу, перемещает её в `4_in_progress/`, `status` → `in_progress`.
- **Git:** переключиться на ветку задачи, закоммитить: `task(001): start work`

### Завершение задачи (done)
- **Условие:** задача выполнена, код протестирован, PR принят (если применимо).
- **Действие:** файл перемещается в `5_done/`, `status` → `done`, `updated_at` обновляется.
- **Git:** сделать коммит (если есть изменения), смержить ветку, удалить её (опционально). Коммит: `task(001): complete`

### Блокировка задачи
- **Ситуация:** задача в `in_progress` требует уточнений или внешних данных.
- **Действие:** 
  - В frontmatter задачи проставляется `blocked_by: "002"` (ID новой задачи-блокера).
  - Создаётся новая задача в `1_sketch` или `2_design` с кратким описанием того, что нужно уточнить.
  - Основная задача остаётся в `in_progress`, но агент переключается на блокер.
- **Снятие блокировки:** после выполнения блокера `blocked_by` основой задачи устанавливается в `null`.

### Откладывание задачи
- **Ситуация:** задача перестаёт быть приоритетной или не может быть выполнена сейчас.
- **Действие:** файл перемещается в `0_backlog/`, `status` → `backlog`.
- **Git коммит:** `task(001): move to backlog`

## Порядок работы агента

1. **Прочитать контекст:** `concept.md`, `tech_stack.md`, `RULES.md`, `STRUCT.md` (если есть).
2. **Проверить `4_in_progress/`:**
   - Если есть задача – работать над ней.
   - Если задача заблокирована (`blocked_by` не null) – переключиться на задачу-блокер (найти её в `1_sketch` или `2_design`).
3. **Если `in_progress` пуст:** взять задачу с наивысшим приоритетом из `3_todo/` и переместить в `in_progress`.
4. **Если `todo` пуст:** предложить пользователю создать новые задачи или пересмотреть дизайн.
5. **После выполнения задачи:**
   - Обновить frontmatter (дата, статус).
   - Переместить файл в `5_done/`.
   - Сделать коммит.
   - Создать/обновить PR (если требуется).
6. **При возникновении неясностей:** создать задачу-блокер, но не возвращать текущую задачу назад.

## Запрещённые действия
- Перемещать задачу из `in_progress` обратно в `design` или `sketch`.
- Работать над несколькими задачами одновременно (держать более одного файла в `in_progress`).
- Изменять задачу вручную без обновления frontmatter (использовать `forge task move`).
- Коммитить изменения без соответствующего сообщения (должно быть понятно, какая задача и что сделано).

## Шаблон сообщения для коммитов (для человека/агента)
- Добавление задачи: `task(001): add sketch "Brief title"`
- Перемещение: `task(001): move from sketch to design`
- Начало работы: `task(001): start work`
- Завершение: `task(001): complete`
- Блокировка: `task(001): blocked by 002`
- Откладывание: `task(001): move to backlog`
```


```text
# workflows/git.md

## Роль этого файла
Описывает правила работы с Git для ИИ-агента и человека: именование веток, формат коммитов, работа с PR, слияние.

## Общие положения
- Все изменения кода должны быть связаны с задачей из `tasks/`.
- Каждый коммит должен иметь осмысленное сообщение, начинающееся с идентификатора задачи (например, `task(001): ...`).
- Основная ветка – `main` (или `master`). Запрещено коммитить напрямую в `main`.

## Ветвление

### Типы веток
| Тип       | Префикс      | Пример                              | Применение                                   |
|-----------|--------------|-------------------------------------|----------------------------------------------|
| feature   | `feature/`   | `feature/001_auth_login`            | Новая функциональность (из `tasks/2_design`) |
| fix       | `fix/`       | `fix/042_button_color`              | Исправление бага (часто сразу в `todo`)      |
| spike     | `spike/`     | `spike/015_cache_performance`       | Исследование, прототип (может не дойти до PR)|
| chore     | `chore/`     | `chore/099_update_docs`             | Служебные задачи (документация, CI)          |

### Правила именования
- После префикса – ID задачи и краткое название через подчёркивание (slug).
- Название только латиница, максимум 50 символов.
- Пример: `feature/001_add_user_profile_page`

### Создание ветки
- Ветка создаётся при переходе задачи из `design` в `todo` (автоматически командой `forge task move <id> todo`).
- Если ветка уже существует (например, для блокера), использовать её.

## Коммиты

### Формат сообщения
```
task(<id>): <type>: <краткое описание>

[optional body]
```
- `<id>` – номер задачи (три цифры, например `001`).
- `<type>` – один из: `add`, `update`, `fix`, `refactor`, `docs`, `test`, `chore`.
- Пример: `task(001): add: implement login endpoint`

### Правила
- Один коммит – одно логическое изменение.
- Сообщение на английском (или русском, но единообразно).
- Длина первой строки ≤ 72 символов.
- Тело коммита (если нужно) отделяется пустой строкой и описывает **почему**, а не **что**.

### Автоматические коммиты от `forge`
- Утилита `forge` никогда не делает коммиты автоматически. Она только выводит команду, которую должен выполнить пользователь (или агент с подтверждением).
- Пример вывода: `git add tasks/4_in_progress/001_auth.md && git commit -m "task(001): start work"`

## Pull Request (PR) процесс

### Когда создавать PR
- Когда задача в `in_progress` завершена и код готов к ревью.
- Агент (или человек) создаёт PR из ветки задачи в `main`.

### Требования к PR
- Название PR: `[task 001] Add auth login`
- Описание PR: должно содержать ссылку на файл задачи и краткое описание изменений.
- PR не должен содержать более 400 строк изменений (если больше – разбить на несколько задач).

### Кто ревьюит
- Для проектов с командой – как минимум один аппрув другого разработчика.
- Для соло-проекта – агент может выполнить самопроверку (прогнать тесты, линтеры), но PR всё равно создаётся для истории.

### Процесс слияния
- После аппрува и успешного CI – мержить через `rebase and merge` или `squash and merge` (решает команда).
- После мержа ветка задачи удаляется (локально и на удалённом репозитории).
- Задача перемещается в `5_done/`.

## Примеры команд для агента (шаблоны)

### Начать работу над задачей
```bash
git checkout main
git pull
git checkout -b feature/001_auth_login
git add tasks/4_in_progress/001_auth_login.md
git commit -m "task(001): start work"
```

### Завершить задачу и создать PR
```bash
git add .
git commit -m "task(001): complete: implement login with JWT"
git push -u origin feature/001_auth_login
gh pr create --title "[task 001] Add auth login" --body "Closes #001" --base main
```

### Исправить баг (прямо в `todo`)
```bash
git checkout main
git pull
git checkout -b fix/042_button_color
git add tasks/3_todo/042_button_color.md
git commit -m "task(042): start fix"
```

## Запрещённые действия
- Коммитить изменения, не связанные с задачей.
- Использовать `--force` push в общих ветках.
- Мержить свой PR без ревью (исключение – экстренные фиксы с подтверждением).
- Оставлять ветку после мержа не удалённой.

## Интеграция с `forge`
Утилита `forge` предоставляет команды, которые помогают соблюдать эти правила:
- `forge task move <id> todo` – создаёт ветку (если нет) и переключает на неё.
- `forge task done` – проверяет, что ветка синхронизирована, и предлагает команды для PR.
- `forge task branch` – показывает текущую ветку и связанную задачу.

Агент должен использовать эти команды вместо ручных git-операций, чтобы избежать ошибок.
