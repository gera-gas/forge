# Decision — Kanban Board Design

Дата принятия решения: 2025-04-14

## Краткое резюме

Принято решение о внедрении Kanban-доски со стадиями дизайна и реализации в утилиту `forge`. Это позволит структурировать workflow разработки от идеи до кода, с чётким разделением фаз дизайна и реализации.

---

## Принятые решения

### 1. Название корневой папки
**Решение:** `kanban/` — используется в текущей структуре проекта, интуитивно понятно для пользователей.

### 2. Структура стадий
**Решение:** Плоская структура с числовыми префиксами для сортировки:

```
kanban/
├── 0_backlog/      # Отложенные задачи
├── 1_sketch/       # Идеи, user stories, наброски
├── 2_design/       # Утверждённый дизайн, ТЗ
├── 3_todo/         # Технически проработанные задачи, готовые к коду
├── 4_in_progress/  # В работе (не более одной)
└── 5_done/         # Завершённые задачи # NOTE: кстати по финалу можно формировать доки в .agent/specs ну или после 2_design, если это не код.
```

**Почему:** Простота, сортировка работает из коробку, LLM-friendly.

### 3. Организация задач внутри стадии
**Решение:** Гибридный подход — один файл для простых задач, папка для сложных.

- Простая задача: `001_simple_task.md`
- Сложная задача: `001/` (папка с несколькими файлами)

**Правила нумерации файлов внутри папки:**
- `0_<name>.md` — всегда точка входа (проблема, идея, user story)
- `1_<name>.md`, `2_<name>.md` — итерации/обсуждения
- Последний файл с суффиксом `_decision` или `_summary` — итоговое решение
- Файлы без номера — приложения (диаграммы, спецификации и т.д.)

**Почему:** Агент всегда читает `0_*` первым, порядок соблюдён, есть семантика.

### 4. Frontmatter
**Решение:** Минимальный YAML (без дублирования status/stage):

```yaml
---
id: "001"
title: "Краткое название"
type: "feature"     # feature | fix | spike | chore
priority: "medium"  # low | medium | high | critical
blocked_by: null
tags: []
---
```

**Статус и стадия НЕ дублируются** — они определяются расположением файла в папке.

**Почему:** Уменьшение рассинхрона между YAML и файловой системой.

### 5. Git-интеграция

#### Ветвление
**Решение:** Ветка отражает суть задачи, а не её стадию.

- `feature/<id>_<slug>` — новая функциональность
- `fix/<id>_<slug>` — исправление бага
- `spike/<id>_<slug>` — исследование/прототип
- `chore/<id>_<slug>` — служебные задачи

#### Коммиты при перемещении задач
**Решение:** Task-ориентированный формат с использованием `->` (не служебный символ).

Примеры:
- `task(001): add sketch "Kanban board"`
- `task(001): move sketch -> design`
- `task(001): start work`
- `task(001): complete`

**Почему `->`:** Не является служебным символом в bash/cmd/powershell, легко набирается с клавиатуры, читаемый.

### 6. Обратная совместимость
**Решение:** Старая папка `.agent/tasks/` помечается как deprecated.

- В текущем проекте `forge`: старые задачи остаются в `tasks/` (история)
- В реализации утилиты `forge init`: создаётся только `kanban/`, без `tasks/`
- Пометка добавляется в `.agent/README.md`

### 7. Документация
**Решение:** Краткие правила в корневом `.agent/README.md`, позже — полноценный `docs/user_guide.md`.

**Стандарт пометок в скетчах:** Для добавления заметок в скетчах использовать Markdown blockquote:
```markdown
> **NOTE:** текст заметки
```
Это стандартный Markdown, красиво рендерится, легко ищется grep'ом.

### 8. Расширения (для будущего)
**Решение:** Записать идеи для будущих скетчей:

- **Скетч 002:** VSCode Extension — графическая Kanban-доска с drag & drop, интеграция с OpenRouter, вопрос про сайт/маркетплейс для дистрибуции.
- **Future:** WebUI, интеграция с другими IDE, мобильное приложение.

## Риски и митигации

| Риск | Митигация |
|------|-----------|
| Агент путается в нумерации файлов | Формализовать правило в README, добавить примеры |
| Пользователи не хотят мигрировать с tasks/ | В текущем проекте оставить tasks/ как deprecated, в реализации forge — только kanban/ |
| Сложные задачи в одной папке растянутся | Ограничить количество файлов, использовать вложенность для больших спеков |
| Git-ветки дублируются при перемещении задач | Проверять существование ветки перед созданием |

## Дополнительные решения

### Автогенерация спецификаций
При переходе задачи из `2_design` в `3_todo` автоматически генерировать спецификацию в `.agent/specs/`. При завершении задачи (`5_done`) — обновлять/финализировать спецификацию. Это можно реализовать как хук в команде `forge task move`.
