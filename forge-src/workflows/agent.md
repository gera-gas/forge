# Рабочий процесс для агента

1. Прочитай `README.md`, `concept.md`, `tech_stack.md`, `rules.md`.
2. Проверь `kanban/4_in_progress/`. Если есть задача – работай над ней. Если нет – возьми первую из `kanban/3_todo/` и перемести в `4_in_progress/`.
3. Перед началом реализации задачи прочитай `struct.md` (если есть) и соответствующие `specs/`.
4. После выполнения:
   - Обнови файл задачи (добавь дату завершения, результат).
   - **Запроси у пользователя подтверждение** на перенос задачи в `5_done/`.
   - Если пользователь подтвердил — перемести задачу в `kanban/5_done/`.
   - Если пользователь не подтвердил — оставь задачу в `kanban/4_in_progress/` для доработки.
   - Сделай коммит с сообщением `task(<id>): complete`.
   - Если нужен PR – создай его и запроси ревью.
5. Для Git-операций следуй `workflows/git.md`.

> **Важно:** Переход `in_progress → done` требует подтверждения пользователя (человека).
> Агент может рекомендовать перенос, но финальное решение принимает разработчик.

## Работа со скетчами (1_sketch/)

### Декомпозиция многоФазных скетчей

Если скетч содержит несколько независимых направлений или фаз:

1. Прочитай `0_base_idea.md` (или основной файл скетча).
2. Определи независимые направления/фичи.
3. **Предложи пользователю декомпозицию** — какие части вынести в отдельные файлы.
4. **Дождись подтверждения пользователя** перед разделением.
5. Создай дочерние файлы с нумерацией: `1_<slug>.md`, `2_<slug>.md`, ...
6. `0_base_idea.md` остаётся как зонтичный документ с общим видением и ссылками на дочерние файлы.

### Правила

- **Один файл = одна цель/фича/направление.**
- Фазы (MVP, Phase 2, Phase 3+) внутри файла — это приоритизация, не разделение.
- При переходе `sketch → design` берётся только MVP-часть.
- Открытые вопросы обсуждаются с пользователем. Решения записываются в скетч.
