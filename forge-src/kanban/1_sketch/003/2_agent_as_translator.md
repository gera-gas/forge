# ИИ-агент как транслятор спецификации в код

**Приоритет:** Phase 2  
**Родитель:** [0_base_idea.md](0_base_idea.md)

---

## Цель

Определить роль ИИ-агента в экосистеме Forge. Агент — не «компилятор» (детерминированный), а **транслятор** спецификации в одну из возможных реализаций.

---

## Парадигма: спецификация → реализация

### Традиционная разработка

```
Исходный код (.rs, .c, .py) → Компилятор → Бинарник
```

Код — источник истины. Компилятор детерминирован: тот же код → тот же бинарник.

### Парадигма Forge

```
Спецификация (forge-src/*.md) → ИИ-агент → Код (.rs, .c) → Компилятор → Бинарник
```

Спецификация — источник истины. ИИ-агент **недетерминирован**: та же спецификация → разные варианты реализации (с разным качеством, стилем, структурой).

### Почему не «компилятор»

| Свойство | Компилятор (gcc, cargo) | ИИ-агент |
|----------|-------------------------|----------|
| Детерминизм | Тот же вход → тот же выход | Тот же вход → разный выход |
| Воспроизводимость | 100% | ~70-90% |
| Корректность | Гарантирована | Не гарантирована, требует проверки |
| Реверс | Потеря смысла | `forge wrap` может потерять нюансы |
| Скорость | Миллисекунды | Секунды/минуты |

**Вывод:** ИИ-агент — это **транслятор**, а не компилятор. Он переводит спецификацию на человеческом языке в код на языке программирования. Результат требует проверки (компиляция, тесты, ревью).

## Входные данные агента

ИИ-агент читает `forge-src/` как структурированный контекст:

| Файл | Роль для агента | Аналог |
|------|-----------------|--------|
| `concept.md` | Что строим (цели, ограничения) | Requirements |
| `tech_stack.md` | На чём строим (язык, библиотеки) | Build config |
| `struct.md` | Как организовано (модули) | Architecture |
| `rules.md` | Стандарты кодирования | Linter config |
| `codegen.md` | Правила генерации (как переводить) | Compiler flags |
| `kanban/` | Что делать сейчас (задачи) | Task queue |
| `workflows/` | Как работать (процессы) | CI/CD pipeline |

---

## Выходные данные агента

| Тип | Пример | Куда |
|-----|--------|------|
| Исходный код | `src/main.rs`, `src/cli/init.rs` | `src/` проекта |
| Тесты | `tests/integration_test.rs` | `tests/` проекта |
| Файлы сборки | `Cargo.toml`, `CMakeLists.txt` | Корень проекта |
| Документация | `README.md`, комментарии | Разные места |
| Git-операции | Коммиты, ветки | Git |

## Режимы работы агента

### Режим 1: Интерактивный (Interactive)

Пользователь даёт задачу → агент работает в диалоге:

```
Пользователь: forge agent "Реализуй команду forge wrap"
Агент:
  1. Читает forge-src/ (concept, tech_stack, struct, rules, codegen)
  2. Читает задачу из kanban/4_in_progress/
  3. Планирует изменения
  4. Генерирует код
  5. Запускает cargo build
  6. Запускает cargo test
  7. Сообщает результат
```

### Режим 2: Автономный (Autonomous)

Агент берёт задачу из kanban и работает сам:

```
forge agent --auto
  1. Находит задачу в kanban/3_todo/
  2. Перемещает в kanban/4_in_progress/
  3. Читает контекст
  4. Генерирует код
  5. Тестирует
  6. Запрашивает подтверждение (in_progress → done)
```

### Режим 3: Мульти-агентный (Multi-agent)

Разделение на роли (см. [скетч 002/2_multi_agent.md](../../002/2_multi_agent.md)):

```
forge agent --multi
  Arch: читает sketch → создаёт design
  Dev:  читает design → пишет код
  Ops:  читает код → коммитит, тестирует
```

## Эволюция agent layer

### Phase 2a: `forge agent` как подкоманда

```rust
// src/main.rs
Commands::Agent {
    query: Option<String>,    // Задача текстом
    auto: bool,               // Автономный режим
    multi: bool,              // Мульти-агентный режим
}
```

- Один бинарник `forge`
- Агент — модуль `src/agent/` внутри CLI
- LLM-вызовы через `src/llm/`
- Чтение контекста через существующие модули

### Phase 2b: Multi-agent (Arch / Dev / Ops)

- Оркестратор на правилах (без LLM)
- Роли в `forge-src/roles/<role>.md`
- Маппинг ролей на стадии kanban (см. скетч 002)

### Phase 3: `forge-agent` как отдельный бинарник

- Выделить `forge-core` как библиотеку
- `forge-agent` — отдельный бинарник, зависит от `forge-core`
- Независимые релизы, разные циклы разработки
- `forge` CLI остаётся менеджером спецификаций
- `forge-agent` — транслятор спецификации в код

## Контроль качества

Поскольку ИИ-агент недетерминирован, результат требует проверки:

| Проверка | Кто | Когда |
|----------|-----|-------|
| Компиляция (`cargo build`) | Агент (автоматически) | После генерации |
| Тесты (`cargo test`) | Агент (автоматически) | После генерации |
| Линтер (`cargo clippy`) | Агент (автоматически) | После генерации |
| Code review | Человек | Перед `in_progress → done` |
| Подтверждение завершения | Человек | `in_progress → done` (правило kanban) |

## Решения по открытым вопросам

| Вопрос | Решение | Обоснование |
|--------|---------|-------------|
| Агент = компилятор? | **Нет, транслятор** | Недетерминирован, результат требует проверки |
| Где живёт агент? | **Phase 2: подкоманда `forge agent`**, Phase 3: отдельный бинарник | Начать просто, разделить при росте |
| Автономный режим? | **Да, но с подтверждением done** | Человек контролирует завершение |
| Multi-agent? | **Phase 2b**, оркестратор на правилах | См. скетч 002/2_multi_agent.md |
| Контроль качества | **Компиляция + тесты + ревью** | ИИ может ошибаться, нужна проверка |
