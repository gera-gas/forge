## 1. Название: makerforge

Норм, но две поправки:

- Проверь на crates.io не только `forge`, но и `makerforge`, `mf`, `mkf` — я не могу посмотреть актуальный реестр, там всё меняется быстро.
- **Имя пакета ≠ имя команды.** В Cargo.toml пакет может называться `makerforge`, а бинарник — короче. Набирать `makerforge codegen --role developer` 40 раз в день — надоест. Сделай `[[bin]] name = "mf"`, команда станет `mf add`, `mf status`. Короткий вызов — это не мелочь, это половина удовольствия от CLI.

## 2. GitVibeOps → GitAgentOps

Переименовывай. «Vibe» — маркетинговый мем, а суть твоей практики другая: **агенты работают, git фиксирует и показывает состояние**. GitAgentOps честнее. Но один совет: не цепляйся за термин на этапе разработки — это ярлык для наружного мира, он появится сам, когда практика оформится. Внутри проекта просто опиши правила в `workflow/git.md`.

## 3. Плагинная шина JSON и MCP — в чём разница

Да, MCP — это протокол для агентов, и полезно понять, где он пересекается с твоими планами, а где нет.

**MCP (Model Context Protocol)** — открытый стандарт: JSON-RPC 2.0 поверх stdio или HTTP. Хост (Claude Desktop, IDE, агентский CLI) запускает *серверы*, которые отдают модели три вещи: **tools** (вызываемые функции), **resources** (контекст/файлы), **prompts** (шаблоны). Смысл стандарта — решить задачу N×M: вместо того чтобы каждая IDE интегрировалась с каждым источником данных, все говорят одним протоколом.

У тебя в проекте MCP может жить в **трёх разных ролях**, и важно их не смешивать:

1. **forge как оркестратор агентов** — вызывает claude-code / aider / deepseek harness как subprocess с собранным контекстом. Это *не* MCP, это просто протокол запуска. Самый простой уровень, с него начнёшь.
2. **forge как MCP-сервер** — выставляет канбан наружу как tools (`task_list`, `task_promote`) и forge-src как resources. Тогда Claude Code или Cursor *сами* найдут твои задачи и смогут двигать их. Это, кстати, почти бесплатная интеграция с VS Code — сильный ход на позднем этапе.
3. **forge-плагины** (метрики, Mojo-лаба) — своя простая шина. Достаточно JSON-RPC-подобных сообщений:

```
→ {"id":1, "method":"initialize", "params":{"protocol":"1"}}
← {"id":1, "result":{"name":"metrics","version":"0.1"}}
→ {"id":2, "method":"scan", "params":{"root":"forge-src"}}
← {"id":2, "result":{"findings":[...]}}
```

stdout — протокол, stderr — логи плагина, как в LSP. Регистрация в `.forge/plugins.toml`. Протокол держи близким к JSON-RPC — тогда потом обернуть его в настоящий MCP будет легко.

**Рекомендация:** MVP делается на уровне 1, уровень 3 — минимальный (пара методов), уровень 2 — в конце списка этапов.

## 4. Структура forge-src

Сначала главный принцип, который разрешает половину твоих вопросов 4.3–4.5:

> **У каждого факта — ровно одно место истины.** Статус задачи — её папка. Даты — git. Идентичность — ID. Связи — `parent`. Всё, что продублировано, однажды разъедется, и тогда понадобится `san` просто для поиска рассинхрона.

### 4.1 README.md

Да, но добавь в **корень проекта** маленький `AGENTS.md` (это фактический стандарт, который читают Claude Code, Codex и т.п.) с одной строкой: «Начни с forge-src/README.md». Не дублируй содержимое — просто указатель.

### 4.2 concept.md

Хорошо, закрепи структуру:

- **Vision** — зачем проект существует.
- **Non-goals** — что сознательно не делаем (твоё «что не хотим видеть»).
- **Success criteria** — как поймём, что получилось.
- **Constraints** — жёсткие рамки.

### 4.3 Канбан и frontmatter

Папки-стадии — правильно, перемещение задачи = `git mv`, и история переходов пишется сама. Но в твоём frontmatter есть лишнее:

| Поле | Вердикт | Почему |
|---|---|---|
| `id` | оставить | первичный ключ |
| `title` | оставить | |
| `parent` | оставить | связи — дерево задач |
| `epic` | **добавить** | группировка для `spec` и фильтров |
| `role`, `assignee` | оставить | |
| `status` | **убрать** | статус = папка. Дубль = рассинхрон |
| `uuid` | **убрать** (на MVP) | id достаточно; uuid нужен только при миграции между репо |
| `created`/`updated` | **убрать** | это знает git, и точнее |
| `outcome` | добавить | только при закрытии: `done` / `cancelled` / `rejected` |

Итог:

```yaml
---
id: T-0007
title: UART драйвер с DMA
parent: T-0002
epic: drivers
role: developer
assignee: ai
---
```

**Задача = папка** `T-0007-uart-driver/` с файлами внутри. Префикс `0_base_idea.md` не нужен — порядок чтения агентом опиши в `workflow/agent.md` («читай idea.md, потом design.md»). Внутри: `idea.md` → по мере взросления добавляются `design.md`, `notes.md` и т.д.

### 4.3.1 spec из done — генерировать, не копировать

Ключевое различие: **done — это журнал (append-only, история), spec — это снимок текущего состояния**. Это два разных артефакта, и руками их синхронизировать — ошибка.

Сделай `makerforge spec` командой генерации: она собирает из done актуальное состояние по эпикам (`epic: drivers` → `docs/spec/drivers.md`), агент может переписывать текст в обзорном стиле. Файл помечается `<!-- auto-generated by mf spec -->` и коммитится. DRY действует и на документацию: done — источник, spec — view.

### 4.3.2 Где роли — важное возражение

**Не в `.forge/prompts`.** Роли — это часть *командного* контекста, их должен видеть агент и версионировать git. А `.forge` — это личные настройки: какой CLI агента установлен у тебя, токены, пороги. Значит:

```
forge-src/roles/     → architect.md, developer.md, reviewer.md, devops.md  (в git)
.forge/config.toml   → провайдер, команды запуска, пороги san              (в .gitignore)
```

Твоя командная схема `mf plan --role architect` при этом остаётся как есть — просто файл роль читается из forge-src.

### 4.4 Метрики и san — два уровня

Сначала спека метрик, язык потом:

**Уровень 1 (ядро, Rust, без Mojo) — команда `mf san`:**
- возраст задачи в стадии — из `git log` последнего перемещения: «T-0012 висит inprogress 14 дней → WARN»;
- WIP-затор: в `4_inprogress` больше K задач;
- осиротевшие `parent` (указывает на несуществующий id);
- дубликаты заголовков, битые md-ссылки;
- бюджет контекста: суммарный размер forge-src в «токенах» (≈ символы/4) выше порога — «контекст разрастается».

Вывод как у компилятора: `WARN [T-0012] inprogress: 14d`. Пороги — в `.forge/config.toml`.

**Уровень 2 (плагин, вот тут Mojo уместен):** дубли между .md — шинглинг + MinHash по n-граммам, это уже числодробилка. Формат протокола из п.3, и Mojo-лаба получает настоящую задачу вместо выдуманной.

### 4.5 Мелкие задачи — fast path, но ID единый

Интуиция верная: не тащить «переименовать функцию» через sketch и design. Но **префиксы Plan-001/Dev-001 — не делай**, это антипаттерн:

1. ID — первичный ключ. Меняющийся ключ ломает все ссылки: `parent`, теги в коммитах, ссылки из ADR.
2. История задачи разорвётся на два grep: старые коммиты помечены `Plan-001`, новые `Dev-001`.
3. Стадия и так видна — из папки и git-истории, дублировать её в ID незачем.

Правильно: **ID глобальный и выдаётся один раз при рождении, в любой стадии**. Мелкая задача создаётся сразу в `3_todo` с `parent` на эпик или задачу-источник. Правило пропишу так: *меняет архитектуру → через design (и возможно ADR); не меняет → сразу todo*. Счётчик ID — в `forge-src/manifest.toml` (там же: версия схемы, список эпиков).

### 4.6 workflow/ — что добавить

- `agent.md` — как агент читает контекст, порядок файлов, лимиты, что делать при конфликте. У тебя есть.
- `git.md` — конвенции коммитов/веток. Есть.
- **`escalation.md` — когда агент обязан остановиться и спросить человека.** Это важнее всего остального: guardrails от самовольных решений.
- `review.md` — критерии готовности, чеклист ревью.
- `testing.md` — когда юнит-тесты обязательны.

Больше на старте не надо — workflow раздувается быстрее всего.

### 4.7 Теги в коммитах — да, и это почти бесплатно

Формат: `[T-0007: sketch->design] описание` — бери его. Приятный бонус: **`git log --grep="T-0007"` уже работает из коробки**, никакой БД не нужно. Правила:

- каждый переход стадии = `git mv` + авто-коммит с тегом (это делает `mf move`);
- каждый коммит *кода* обязан нести ID активной задачи — тогда код и задачи связаны навсегда;
- `mf show T-0007` = биография: коммиты по grep + перемещения папки = готовый таймлайн.

Проверку конвенции можно добавить в `mf validate` позже (коммит-линтер), на MVP хватит дисциплины.

### 4.8 ADR и codegen

**ADR (Architecture Decision Record)** — короткий документ, отвечающий на вопрос «*почему* принято именно такое решение». Не «что сделано» (это в задачах), а «почему»: обычно секции Status / Context / Decision / Consequences. Нумеруются сквозя, **никогда не переписываются** — устаревший помечается `status: superseded by 0012`. Кладутся в `forge-src/adr/0007-async-runtime.md`. ADR — естественный *результат* стадии design: задача в design либо ссылается на существующий ADR, либо рождает новый.

Для остального — разделяй неизменяемое и изменяемое:

```
forge-src/codegen/
  rules.md      — общие правила качества (DRY, KISS, обработка ошибок) — меняется редко
  stack.md      — языки, версии, платформы — меняется
  build.md      — сборка, тесты, deploy — меняется
  lang/c.md     — языковые правила, заводить по мере появления языков
```

## 5. Карта команд

Принципы: **существительные — просмотр, глаголы — действие; каждая мутация = коммит с тегом; у всех команд чтения флаг `--json`** (будущий TUI/VS Code будут питаться теми же данными).

| Группа | Команды |
|---|---|
| Проект | `new <name>`, `init`, `wrap` (код → forge-src через агента, поздний этап) |
| Задачи | `add "title" [--stage todo] [--parent T-0002]`, `move T-0007 <stage>` (перемещение + автокоммит), `list`, `show T-0007`, `close T-0007 --outcome cancelled` |
| Агенты | `plan --role architect`, `codegen --role developer`, `review --role reviewer` |
| Наблюдение | `status`, `log [T-0007]`, `spec` (генерация из done) |
| Гигиена | `validate` (схема), `doctor` (окружение: git, агент, версии), `san` (гигиена задач) |

Семантика, о которой ты спрашивал:

- **`status` — настоящее**: срез «где мы» — счётчики по стадиям, WIP, эпики, последнее движение, свежие ADR.
- **`log` — прошлое**: поток событий из git-истории, фильтры по id/эпику/стадии.
- **`san`** — отличное имя, бери. Уровень 1 в ядре, уровень 2 (дубли) — плагин из п.4.4.

## Что это меняет в плане

Практически ничего ломать не надо, только уточнить:

- Этап 0: добавить `manifest.toml` (схема, эпики, счётчик ID) и финальный frontmatter без `status/uuid`.
- Этап 1 (MVP на Rust): `new/init/validate/list/doctor` + **`add`/`move` с автокоммитами** — это сердце GitAgentOps, оно должно появиться рано, а не в этапе про git.
- Этап 3: `status`/`log` — уже обёртки над git, наработанные `move`-коммитами.
- Этап 4: `san` уровня 1.
- Этап 5–6: TUI, `spec`, Mojo-плагин, MCP-фасад, `wrap`.

Самое ценное, что родилось в этом обходе: **ID навсегда + мутации через автокоммиты + одно место истины на факт**. Эти три правила дают тебе дашборд, таймлайны и гигиену почти без дополнительного кода — всё выводится из git.
