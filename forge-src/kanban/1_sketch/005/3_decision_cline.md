# Decision — Оптимизация forge-src и отказ от Mojo (синтез рассуждений GLM / DeepSeek)

Дата принятия решения: 2026-09-04

## Краткое резюме

Рассмотрены три рассуждения из скетча 005 (`1_deepseek_idea.md`, `1_glm_idea.md`, `2_deepseek_mojo_idea.md`) о развитии утилиты `forge` и структуре `forge-src/`. Модели не знали о текущем состоянии кода, поэтому значительная часть предложений уже реализована. Итог: **Mojo полностью исключаем**, ядро идеи GLM («ID навсегда + мутации через автокоммиты + одно место истины на факт») принимаем — первые два из трёх правил уже работают, недостающее звено (автокоммиты в CLI) становится приоритетом №1. Плагины/MCP и LLM-команды внутри forge — отложены как противоречащие парадигме проекта (ADR-001, ADR-005).

## Принято (что берём)

### 1. Автокоммиты при мутациях задач — приоритет №1 (GLM, п. 4.7)

Сердце практики «git как источник правды». Сейчас `task move` делает голый `fs::rename` — история переходов теряется.

**Решение:** `task new` и `task move` делают git-коммит затронутых файлов автоматически.

**Формат коммитов — наш, из решения скетча 001** (не GLM-овский `[T-0007: ...]`):

- `task(001): add sketch "Kanban board"`
- `task(001): move sketch -> design`
- `task(001): complete`

**Почему наш формат:** уже принят и применяется в проекте, проще для `git log --grep="task(001)"`, `->` не является служебным символом в bash/cmd/powershell.

Коммит только если репозиторий существует и есть изменения; ошибка git не ломает выполнение команды (предупреждение).

### 2. «Биография задачи» — история в `task show` (GLM, п. 4.7)

`forge task show 001` дополняется секцией истории: `git log --grep="task(001)"` + перемещения папки = готовый таймлайн без БД.

### 3. `forge status` — срез «настоящее» (GLM, п. 5)

Счётчики задач по стадиям, WIP-загрузка, текущая задача, последнее движение по доске. Подмножество уже доступно через `task list` — `status` делает сводку.

### 4. `forge log [id]` — «прошлое» (GLM, п. 5)

Поток событий из git-истории, фильтр по ID задачи. Обёртка над git, работающая за счёт автокоммитов из п. 1.

### 5. `forge san` — гигиена, уровень 1, чистый Rust (GLM, п. 4.4)

Сначала спека метрик, язык потом:

- возраст задачи в текущей стадии (из git log последнего перемещения): `WARN [005] in_progress: 14d`;
- WIP-затор: в `4_in_progress` больше N задач;
- битые ссылки (`parent`, `blocked_by` на несуществующий ID);
- дубликаты заголовков;
- бюджет контекста: суммарный размер `forge-src` в «токенах» (≈ символы/4).

Вывод в стиле компилятора: `WARN [T-0012] in_progress: 14d`. Пороги — в конфиге (позже).

### 6. `forge validate` — проверка схемы (GLM, п. 5)

Валидация frontmatter (обязательные поля, допустимые значения), битых ссылок на design/blocked_by. Коммит-линтер конвенций — позже, на MVP хватает дисциплины.

### 7. Frontmatter: поля `parent` и `epic` — при необходимости (GLM, п. 4.3)

Добавить, когда появятся связанные задачи (`parent`) и группировка для фильтров/`spec` (`epic`). Сейчас не блокирует ничего — не делать заранее.

### 8. `workflows/escalation.md` — guardrails агента (GLM, п. 4.6)

«Когда агент обязан остановиться и спросить человека». Самое ценное из недостающих workflow-файлов. Добавить шаблон в `forge init`. `review.md`, `testing.md` — опционально, при реальной потребности (workflow раздувается быстрее всего).

### 9. Правило ADR: append-only (GLM, п. 4.8)

ADR в `arch.md` не переписываются; устаревшие помечаются `Статус: superseded by ADR-NNN`. ADR — естественный результат стадии design.

### 10. `forge spec` — документация из `5_done` (GLM, п. 4.3.1; поздний этап)

done — журнал (append-only), spec — снимок текущего состояния. Генерировать командой в папку `specs/`, файл помечать `<!-- auto-generated by forge spec -->`. DRY действует и на документацию: done — источник, spec — view.

| LLM-команды `plan`/`codegen`/`review` внутри forge | все | Противоречит ADR-001/005: генерацию выполняет внешний агент (Cline, Claude Code), forge управляет спецификацией. Заглушки `wrap`/`ask` остаются до Phase 2 |

| `manifest.toml` (счётчик ID, схема) | GLM | KISS: сканирующий `next_available_id` работает, лишний файл с рассинхроном не нужен |
| Отдельная папка `adr/` | GLM | `arch.md` одним файлом достаточен при текущем масштабе; правило append-only переносим в него |
| Папка `roles/` | GLM/DeepSeek | Мультиагентности с ролями ещё нет; контекст агента — `codegen.md` + workflows |

| TUI / WebUI / VSCode MCP-фасад | GLM | Не сейчас; VSCode Extension — отдельная тема скетча 002 |
| Задача = только файл или только папка | DeepSeek | Наш гибрид лучше обоих вариантов |

## Итоговая дорожная карта (финальный скетч)

### Этап 1 — Git как источник правды (ядро)
1. Автокоммит в `task new` / `task move` (формат `task(XXX): ...`, скетч 001).
2. История задачи в `task show` (git log --grep).
3. Интеграционные тесты: перемещение в git-репо создаёт коммит с ожидаемым сообщением.

### Этап 2 — Наблюдение
1. `forge status` — сводка по стадиям, WIP, последние движения.
2. `forge log [id]` — события из git, фильтр по ID.
3. `--format json` для обеих команд (единый JSON-контракт, ADR-006).

### Этап 3 — Гигиена
1. `forge san` уровень 1: возраст в стадии, WIP-затор, битые ссылки, дубли заголовков, бюджет контекста.
2. `forge validate`: схема frontmatter, битые design/blocked_by ссылки.

### Этап 4 — Guardrails и документация
1. `workflows/escalation.md` — шаблон в `forge init` и в текущем проекте.
2. Правило superseded — зафиксировать в `arch.md` и в шаблоне README.
3. (опц.) `review.md`, `testing.md` — по потребности.

### Отложено (при появлении потребности)
- Поля `parent` / `epic` во frontmatter и фильтрах.
- `forge spec` — генерация `specs/` из `5_done`.
- `forge doctor` — проверка окружения (git, агент, версии).
- `--format json` для всех команд чтения.
- Плагины / MCP-фасад / VSCode Extension.
- LLM-функции (`wrap`, `ask`) — Phase 2.
- Mojo — исключён.

## Риски и митигации

| Риск | Митигация |
|------|-----------|
| Автокоммит в не-git каталоге падает | Проверять наличие `.git`; без репо — просто предупреждение |
| Автокоммит затрагивает чужие незакоммиченные файлы | Коммитить только пути задачи (`git add <path>`) |
| `san` требует git-историю, а её нет (задачи до Этапа 1) | Возраст в стадии — fallback «неизвестно» вместо WARN |
| Дублирование логики `status` и `task list` | `status` переиспользует `scan_all_tasks` |
| Раздувание workflows при добавлении файлов | Новые workflow-файлы — только по реальной потребности |
