## 1. Название утилиты: makerforge

`forge` действительно занят в cargo (существует крейт `forge`).  
`makerforge` — рабочее название, но оно длинновато. Возможные варианты:

- `mforge`
- `forge-cli`
- `vibe-forge`
- `agentforge`
- `devforge`
- `specforge`

Но если тебе нравится `makerforge` — используй. Главное, чтобы имя было уникальным в реестрах.  
Я бы предложил `agentforge` или `specforge`, потому что они лучше отражают суть: агент + спецификации.  
`makerforge` звучит как «кузница создателя», тоже неплохо, но может быть менее очевидно для других.

---

## 2. GitVibeOps → GitAgentOps?

Оба названия имеют право на жизнь.

- **GitVibeOps** — отсылка к vibe coding, более модно и узнаваемо, но может звучать несерьёзно.
- **GitAgentOps** — более профессионально, подчёркивает, что движущая сила — агенты (ИИ), а не просто "вайб".  
  Я бы рекомендовал **GitAgentOps**, так как проект ориентирован на агентов и автоматизацию, и это название будет лучше принято в корпоративной среде и среди инженеров.

Но можно использовать оба: GitVibeOps как маркетинговый слоган, GitAgentOps как технический термин практики.

## 3. Плагиновая система в JSON (аналогия с MCP)

Ты спрашиваешь: «плагиновая система в JSON, которая как в MCP — это же протокол для агентов?»

Да, MCP (Model Context Protocol) — это открытый протокол, позволяющий LLM-агентам взаимодействовать с внешними инструментами и источниками данных через стандартизированный интерфейс (обычно JSON-RPC).  
Ты можешь реализовать упрощённый аналог для своего инструмента.

### Как это могло бы работать в makerforge

В каталоге `.forge/plugins/` лежат JSON-файлы, описывающие возможности плагинов:

```json
{
  "name": "git-log",
  "version": "1.0.0",
  "description": "Get git history for a task",
  "command": "makerforge plugin git-log",
  "inputs": {
    "task_id": {"type": "string", "required": true}
  },
  "outputs": {
    "log": {"type": "string"}
  },
  "permissions": ["read:git"]
}
```

CLI сканирует эту папку и регистрирует команды, которые может вызывать агент.  
Например, когда ИИ хочет получить историю задачи, он вызывает `makerforge plugin git-log --task-id T-001`.  
Это позволяет расширять функциональность без перекомпиляции основной утилиты — плагины могут быть отдельными исполняемыми файлами или скриптами.

### Для чего это нужно?

- Агент сможет сам решать, какие инструменты ему нужны.
- Ты можешь распространять плагины отдельно.
- Упрощается поддержка и расширение.

Но на начальном этапе плагиновая система может быть избыточной. Рекомендую заложить архитектуру с возможностью добавления, но реализовать только после MVP.

## 4. Структура каталога forge-src

Ты предложил много идей, давай разберём каждый пункт и оптимизируем.

### 4.1 README.md внутри forge-src

Да, это правильный подход. В `forge-src/README.md` опиши:

- назначение каталога;
- структуру папок;
- правила именования;
- как использовать файлы;
- соглашения по статусам задач.

Этот README будет первым файлом, который читает ИИ-агент, чтобы понять контекст.

---

### 4.2 concept.md

Отличная идея — отдельный файл с концепцией проекта.  
Предлагаю назвать его `concept.md` или `vision.md`.  
Внутри должно быть:

- Цель проекта (зачем).
- Основные функциональные и нефункциональные требования.
- Ограничения (что не делаем).
- Ключевые архитектурные принципы.

Он служит отправной точкой для генерации других документов, если они отсутствуют.

---

### 4.3 Папка kanban со стадиями

Ты предложил:

- `0_backlog`
- `1_sketch`
- `2_design`
- `3_todo`
- `4_inprogress`
- `5_done`

Это хорошая схема, отражающая жизненный цикл задачи: от идеи до завершения.  
Но нужно учесть несколько моментов:

#### 4.3.1 Из done → spec

Идея формировать из завершённых задач спецификации — интересна.  
Но не стоит автоматически копировать все задачи в `spec`. Лучше вручную или полуавтоматически решать, что является значимой частью системы.  
Можно ввести отдельную папку `spec/` или `docs/` для актуальной документации, которая обновляется по мере завершения задач.  
Например, когда задача по реализации UART драйвера завершена, ты (или агент) обновляешь `spec/uart.md` с описанием API и поведения.  
Это ближе к подходу "документация как код".

#### 4.3.2 Структура подпапок и метаданные

Предложенная структура с подкаталогами `001`, `002` и файлом `0_base_idea.md` — рабочая.  
Но учти, что при перемещении задачи между стадиями будет сложно сохранять историю.  
Лучше использовать плоскую структуру: каждая задача — отдельный файл `T-001.md` в папке стадии.  
А историю переходов хранить в git-коммитах.  
Тогда не нужны подкаталоги `001`, `002` внутри каждой стадии — просто файлы.

Но если хочешь хранить несколько файлов для одной задачи (например, идея, дизайн, реализация), можно делать подпапку с ID задачи внутри стадии.  
Я бы рекомендовал компромисс: на ранних стадиях (sketch, design) задача может быть папкой с несколькими файлами, а на этапе todo и далее — одним файлом.  
Но для простоты начни с одного файла на задачу во всех стадиях. Если нужно больше — добавишь.

Метаданные в frontmatter — это правильно.  
Предлагаю такой набор полей:

```yaml
---
id: T-001
uuid: <hash>
parent: T-000   # если есть родитель
title: Реализовать UART драйвер
status: sketch
assignee: ai
role: developer
created: 2025-01-01
updated: 2025-01-05
---
```

`parent` может ссылаться на ID родительской задачи, если задача порождена из другой.  
`uuid` — хэш для уникальной идентификации при переименованиях.  
`status` дублирует папку, но полезен, если файл перемещается и нужно быстро понять статус без анализа пути.

#### 4.3.3 Связи между задачами

Для отображения цепочек можно использовать поле `parent` или `related`.  
В git-коммитах можно писать `[T-001: sketch -> design]`, как ты предложил.  
Это позволит через `git log` видеть историю.

---

### 4.4 Очистка от «замусоренных» задач

Идея с лабораторией `forge-labs/mojo-metrics` — интересная, но не стоит выделять отдельный проект на старте.  
Лучше встроить команду `makerforge analyze` (или `makerforge health`), которая анализирует каталог `forge-src` и выдаёт статистику:

- количество задач по стадиям;
- дублирование контента (похожие фразы в разных md);
- «гнилые» задачи (долго не обновлялись, статус не менялся);
- размер контекста (общий объём текста, потенциально перегружает LLM).

Такую команду можно реализовать позже, когда будет накоплена база задач.

---

### 4.5 Нумерация задач: сквозная или по стадиям?

Если задача может миновать некоторые стадии (например, сразу в todo), то сквозная нумерация удобнее: каждая задача получает уникальный `T-XXX` при создании и сохраняет его на всех этапах.  
Папки стадий содержат файлы с этим ID, и при перемещении файл просто переносится.  
Такой подход проще и не требует разных префиксов.

Префиксы типа `Plan-001`, `Dev-001` могут запутать, потому что одна и та же задача может проходить стадии.  
Лучше использовать общий ID задачи, а в frontmatter указывать текущий статус.  
Если нужно различать типы задач (эпик, баг, фича), можно добавить поле `type`.

### 4.6 Структура папки workflow

Ты предложил `git.md` и `agent.md`.  
Предлагаю расширить:

- `git.md` — правила работы с git (как коммитить, именование веток, сообщения коммитов).
- `agent.md` — общие правила для ИИ-агента (как вести себя, этика, стиль).
- `coding-standards.md` — общие принципы качества кода (DRY, SOLID, именование).
- `testing.md` — как писать тесты, требования к покрытию.
- `review.md` — процесс код-ревью.
- `ci-cd.md` — если есть.

Эти файлы будут включаться в промпты при необходимости.

---

### 4.7 Движение по проекту через git

Использовать git как источник правды — отлично.  
Коммиты можно оформлять с префиксом `[T-001: sketch]` или `[T-001: sketch -> design]`.  
Команда `makerforge log --task T-001` будет фильтровать git-историю по этому ID.  
Можно также добавить хук, который автоматически коммитит при смене статуса через CLI.

---

### 4.8 Где хранить архитектуру и ADR

- **ADR** (Architecture Decision Records) — это записи о принятых архитектурных решениях, обычно в папке `docs/adr/` или `decisions/`. Каждый файл содержит контекст, решение, последствия.  
  Предлагаю завести `forge-src/decisions/` с файлами вида `0001-use-rust-for-cli.md`.
- Техническая архитектура (общая схема, модули, взаимодействие) может быть в `forge-src/architecture.md`.
- Стек языков и ограничения — в `forge-src/tech-stack.md` или прямо в `concept.md`.
- Правила сборки, деплоя — в `forge-src/codegen/build-c.md`, `deploy.md` и т.п.

## 5. Группы команд makerforge

Предлагаю разбить команды на функциональные группы.

### Группа «Инициализация и настройка»

- `makerforge new <project-name>` — создать новый проект с готовой структурой `forge-src`.
- `makerforge init` — инициализировать `forge-src` в текущем каталоге (если проект уже существует).
- `makerforge wrap` — проанализировать существующий код и сгенерировать `forge-src` на основе проекта (используя LLM).
- `makerforge config` — просмотр/изменение конфигурации в `.forge/config.toml`.

### Группа «Управление задачами (kanban)»

- `makerforge task add "описание" [--parent T-000] [--role developer]` — создать задачу (по умолчанию в `1_sketch` или `3_todo` в зависимости от ключа).
- `makerforge task move T-001 4_inprogress` — переместить задачу в другую стадию (с git-коммитом).
- `makerforge task list [--status inprogress]` — показать задачи по стадиям.
- `makerforge task show T-001` — показать содержимое задачи.

### Группа «Контекст и генерация»

- `makerforge context build` — собрать контекст из `forge-src` в один файл/JSON для подачи LLM.
- `makerforge plan [--task T-001] [--role architect]` — запустить LLM для создания плана/дизайна задачи.
- `makerforge codegen [--task T-001] [--dry-run]` — сгенерировать код по задаче.
- `makerforge review [--task T-001]` — запустить LLM-ревью кода.

### Группа «GitOps и аналитика»

- `makerforge status` — общий статус: изменённые файлы, текущие задачи, последние коммиты.
- `makerforge log [--task T-001]` — история по задачам из git.
- `makerforge health` — анализ «здоровья» `forge-src` (дубли, устаревшие задачи, размер контекста).
- `makerforge ui` — запустить веб-интерфейс (на будущее).

### Группа «Плагины»

- `makerforge plugin list` — показать доступные плагины.
- `makerforge plugin run <name> [args]` — выполнить плагин.
