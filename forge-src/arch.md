# Architecture Decision Records (ADR)

## ADR-001: Forge — менеджер спецификаций, не только контекста

**Дата:** 2026-08-04  
**Статус:** Принято

### Контекст

Изначально Forge задумывался как CLI-утилита для управления контекстом ИИ-агентов — создание структуры `forge-src/` с шаблонами документации.

В ходе обсуждения (скетч 003) выяснилось, что `forge-src/` файлы могут служить не только контекстом, но и **спецификацией** — основой для генерации кода ИИ-агентом.

### Решение

Forge — менеджер **спецификаций** проекта. Спецификация в `forge-src/` — структурированное описание на человеческом языке, которое:
1. Служит контекстом для ИИ-агентов (как и раньше)
2. Является основой для генерации кода (`forge generate`)
3. Код на ЯП — реализация спецификации, не наоборот

### Последствия

- `forge wrap` = «декомпилятор» (код → спецификация)
- `forge generate` = «транслятор» (спецификация → код)
- `codegen.md` = правила трансляции (новый обязательный файл)
- ИИ-агент = недетерминированный транслятор, не компилятор

## ADR-002: Один бинарник с внутренним разделением

**Дата:** 2026-08-04  
**Статус:** Принято

### Контекст

Возникал вопрос: разделить ли Forge на отдельные инструменты (менеджер контекста + генератор кода) или держать в одном бинарнике.

### Решение

**Один бинарник `forge`** с внутренним разделением на модули:
- `context/` — управление спецификацией (init, wrap, task)
- `codegen/` — генерация кода (generate)
- `llm/` — LLM-интерфейс (общий для wrap и generate)

### Обоснование

- `wrap` и `generate` — обратные операции, делят формат файлов и парсинг
- Разделение = дублирование кода или общая библиотека (сложнее поддерживать)
- Один mental model для пользователя

### Эволюция

- Phase 2: подкоманда `forge agent` внутри того же бинарника
- Phase 3: выделить `forge-core` как библиотеку, `forge-agent` как отдельный бинарник

## ADR-003: Облако и сетевой диск — отложить

**Дата:** 2026-08-04  
**Статус:** Принято

### Контекст

Идея: подключение для работы с общим сетевым диском или облаком для синхронизации `forge-src/` между устройствами.

### Решение

**Отложить до Phase 3+** (Pro tier для команд).

### Обоснование

- **Сетевой диск** — проблематично: блокировки файлов, concurrent-редактирование, нет conflict resolution
- **Облако** — требует backend, auth, API — это Phase 2/3
- **Git уже решает синхронизацию** для соло-разработчика: `forge-src/` коммитится в репозиторий
- Смысл появляется только при командной работе (Pro tier)

### Когда пересмотреть

При переходе к Pro tier (командная работа, синхронизация с Jira/Trello).

## ADR-004: `codegen.md` — обязательный файл

**Дата:** 2026-08-04  
**Статус:** Принято

### Контекст

Нужен файл, описывающий правила, по которым ИИ-агент генерирует код из спецификации.

### Решение

Создать `codegen.md` как **обязательный файл** в `forge-src/`:
- Создаётся при `forge init` из шаблона `src/templates/codegen.md`
- Содержит правила трансляции спецификации в код
- Дополняет `rules.md` (стандарты для человека) правилами для ИИ

### Разделение ответственности

| Файл | Аудитория | Содержание |
|------|-----------|------------|
| `rules.md` | Человек | DRY, KISS, style, обработка ошибок |
| `codegen.md` | ИИ-агент | Процесс генерации, паттерны, проверки, тестирование |

## ADR-005: ИИ-агент — транслятор, не компилятор

**Дата:** 2026-08-04  
**Статус:** Принято

### Контекст

Метафора «ИИ как компилятор» (описание → код) привлекательна, но неточна.

### Решение

ИИ-агент — **транслятор**, не компилятор. Различия:

| Свойство | Компилятор | ИИ-агент |
|----------|-----------|----------|
| Детерминизм | Да | Нет |
| Воспроизводимость | 100% | ~70-90% |
| Корректность | Гарантирована | Требует проверки |

### Последствия

- Результат генерации требует проверки: компиляция, тесты, ревью
- Переход `in_progress → done` требует подтверждения человека (правило kanban)
- `codegen.md` включает обязательные шаги проверки

## ADR-006: CLI и VSCode Extension — JSON-контракт

**Дата:** 2026-08-04  
**Статус:** Принято

### Контекст

Нужно определить, как VSCode Extension взаимодействует с CLI-ядром.

### Решение

- CLI — источник истины (вся бизнес-логика)
- Extension — тонкий GUI-слой (делегирует в CLI)
- Общение через **JSON-вывод** (`--format json`)

### Принципы

1. Extension **не дублирует** бизнес-логику
2. CLI предоставляет JSON-вывод для всех команд
3. Extension парсит JSON и отображает в webview
4. Действия пользователя → команды CLI

### Эволюция

- Phase 1: `child_process` (Extension вызывает CLI)
- Phase 3: рассмотреть WASM (если `forge-core` выделен как библиотека)
